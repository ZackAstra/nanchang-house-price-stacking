# Nanchang Second-Hand Housing Price Prediction: Feature Engineering and Stacking Ensemble

Companion code for the manuscript *"Comparative Study of Second-Hand Housing Price Prediction Based on Machine Learning Regression Algorithms: Feature Engineering and Stacking Ensemble Modeling"*, together with the sample data and the shipped aggregate result files that back the paper's reported numbers.

[中文说明见 README.zh-CN.md](README.zh-CN.md)

## Overview

This repository reproduces the full experimental pipeline of the paper:

- **Data collection**: a four-level crawler for a major Chinese real-estate listing platform (Anjuke, Nanchang) — listing links → listing details → community POI facilities (`main.py`, `src/fetchers/`, `src/parsers/`, `src/storage/`, `config/regions.json`).
- **Feature engineering**: a four-dimensional feature system — physical attributes, POI facilities, geographic accessibility (Accessibility Index), layout structure (Layout Density) — implemented in `src/research/pipeline.py`, plus a 29-label semantic system over listing titles. The rule-based labels are derived in `src/research/llm_semantic_vs_rule_runner.py`; the full LLM annotation reported in the paper (the DeepSeek-V4-Flash labels behind the shipped label CSV and `llm_full_parse_report.json`) was produced through the SiliconFlow batch pipeline — batch input built by `scripts/build_llm_batch_jsonl.py`, output parsed by `scripts/parse_deepseek_full_labels.py` — while `src/research/llm_semantic_extractor.py` implements the Qwen3-32B extraction path used for the cross-model agreement study.
- **Model comparison**: eight baseline regressors, a Stacking ensemble with a Ridge meta-learner, and an OOF-TSRM two-stage residual model, under a fixed temporally sensitive holdout with community-grouped 3-fold cross-validation (`src/research/run_price_research.py`).
- **Error-diagnosis experiments** (paper §5.3): log transformation, label cleaning dose–response, polynomial interactions, quantile regression, information-ceiling diagnosis (`src/research/*_runner.py`).
- **Semantic feature experiments** (paper §5.3): rule-based vs LLM-extracted labels, including prompt×temperature robustness checks (`scripts/build_llm_batch_jsonl.py`, `scripts/run_qwen_prompt_bridge.py`, `scripts/evaluate_llm_3x2_batch.py`).
- **Analyses**: significance matrix with Holm correction, multi-seed summary, computational cost, descriptive statistics, variance decomposition, sensitivity of constructed indices (`scripts/`).
- **Figures**: all paper figures are regenerated by `scripts/generate_figures_review3.py` and `scripts/generate_shap_beeswarm_review3.py` into `docs/figures/`, with the descriptions written to `docs/figures/desc.txt`.

## Headline results

- Final model (log target + rule-based semantic features + StackingRidge): **MAE = 20.17 (×10⁴ CNY), R² = 0.3214** on the extrapolative holdout; R² = 0.68 under a random in-distribution split.
- StackingRidge ranks first in four of five random seeds and significantly outperforms the strongest single model (CatBoost; Holm-corrected p = 4.1 × 10⁻⁷).

Every headline number is backed by a shipped artifact — see [Verification map](#verification-map) below.

## Setup (uv)

```bash
uv venv --python 3.11
uv pip install -r requirements.txt
# crawler only: uv run playwright install chromium
```

The headline results were produced with Python 3.11.10 and the pinned versions in `requirements.txt` (which match `pyproject.toml`). Pin the interpreter explicitly: a bare `uv venv` resolves to whatever Python 3.x is newest on the machine, which is **not** the environment the reported numbers were produced in.

## Quick start (smoke run on the bundled samples)

```bash
uv run python -m src.research.run_price_research \
  --houses data/samples/houses_sample.jsonl \
  --communities data/samples/communities_sample.jsonl \
  --output-dir data/runs --run-id smoke --sample-limit 200 --cv-folds 3
```

This is a **functionality check only**. On the 200-record sample the pipeline keeps 195 usable records and reports an MAE of about 19; which model comes out on top and the exact MAE both depend on the machine's BLAS/threading configuration. Neither the record count nor that MAE appears anywhere in the paper, and the smoke run is not comparable to any reported result. To reproduce the paper's numbers, obtain the full dataset (see below), place it under `data/full/`, and follow the next section.

## Data availability

Following the paper's Data Availability statement:

- **Samples**: 200 stratified records (region × price segment) are bundled under `data/samples/`, including the LLM semantic labels and 10 raw LLM response examples.
- **Aggregate results**: every table value and section statistic reported in the paper is backed by a shipped file under `data/expected_outputs/` or `data/runs/`, so the results can be verified without the raw crawl. The single exception is the base-learner prediction correlation quoted in §5.2 (0.9631 for GradientBoosting–XGBoost): it is not persisted as its own artifact, but it is reproduced exactly from the shipped `model_prediction_errors.csv` (0.963088).
- **Full dataset** (7,140 listings and 1,062 community records, plus the full LLM semantic labels): available from the corresponding author (zhaoxingchen@hotmail.com) upon reasonable request, subject to the original platforms' terms of service. The data were collected from publicly available listing pages and are shared for academic research only.

## Reproducing the paper's tables

The aggregate numbers behind every paper table are shipped under `data/expected_outputs/` and `data/runs/`. To regenerate them from the full dataset (once it is placed under `data/full/`):

1. Run the pipeline with the paper's CV protocol (community-grouped 3-fold). Use the run id `main_seed42` — the figure scripts read `data/runs/main_seed42`:

   ```bash
   uv run python -m src.research.run_price_research \
     --houses data/full/nanchang_houses.jsonl \
     --communities data/full/nanchang_communities.jsonl \
     --output-dir data/runs --run-id main_seed42 --cv-folds 3
   ```

2. Copy the three per-sample intermediates that the analysis scripts read:

   ```bash
   cp data/runs/main_seed42/cleaned_features.csv data/expected_outputs/
   cp data/runs/main_seed42/model_prediction_errors.csv data/expected_outputs/
   cp data/runs/main_seed42/model_experiments.jsonl data/expected_outputs/
   ```

3. Run the analysis scripts (each documents its input and output in its header), e.g. `uv run python scripts/descriptive_stats.py`.

### Table 7 (semantic features)

The headline semantic row is produced by the dedicated runner rather than the main pipeline. With the full dataset and the LLM label CSV in place:

```bash
uv run python -m src.research.llm_semantic_vs_rule_runner \
  --houses data/full/nanchang_houses.jsonl \
  --communities data/full/nanchang_communities.jsonl \
  --llm-features data/full/llm_semantic_features_deepseek_full.csv \
  --output-dir data/runs --run-id semantic_deepseek --cv-folds 3 \
  --only log_rule_semantic
```

This reproduces the headline row (log target + rule-based semantic features + StackingRidge: **MAE = 20.1740, R² = 0.3214**). `--llm-features` is required only when an `llm_*` experiment group is selected — a rule-only reproduction (`--only log_rule_semantic`, `log_area_rule_semantic`, …) runs without the LLM label CSV, which is why that file is not shipped. Dropping `--only` regenerates the whole semantic comparison (~6 experiment groups, several minutes each).

The shipped `data/expected_outputs/semantic_logarea_summary.csv` and `data/expected_outputs/semantic_pair_tests_review5.csv` are regenerated from the shipped per-experiment predictions by `scripts/summarize_semantic_logarea.py` and `scripts/compute_semantic_pair_tests.py`.

Notes:

- `stacking_comparison.csv` holds the semantic-feature experiment (Table 7), **not** the Voting-vs-Stacking comparison, which lives in `voting_vs_stacking_metrics.csv`.
- `combined_experiment_summary.csv` reports the **best model of each configuration** (for the log-target + strict-cleaning run that is LightGBM at MAE 20.4331). Table 6, in contrast, is a fixed-protocol table and quotes the StackingRidge member of the same run (`combined_stacking_ridge`, MAE 20.5346). Both numbers are genuine and come from the same run — they differ only in which member the table reports. Use `combined_model_metrics.csv` to see every member side by side.
- Table 6's remaining rows (moderate / unit-price / total-price cleaning doses, polynomial interactions, quantile regression) are regenerable with the corresponding runners (`label_noise_experiment_runner.py`, `log_transform_experiment_runner.py`, `polynomial_feature_runner.py`, `quantile_regression_runner.py`) and their summary files are shipped as listed above.
- Regenerating on a different machine is **not** bit-reproducible. `RandomForest`/`XGBoost`/`LightGBM` run with `n_jobs=-1`, which perturbs the last few significant digits (we measure ~1e-14) and hence also the tail digits of `significance_matrix.csv`; compare regenerated metrics with a tolerance (1e-6 is ample for MAE), never by byte equality. `compute_cost.csv` also records wall-clock timings (Table 8): its MAE columns reproduce exactly, but the second/ratio columns are hardware-dependent, so treat the reported seconds as indicative and the cost *ratio* as the stable quantity. The Matplotlib SVGs embed a creation timestamp and randomised `clip-path` ids, so only the PNGs are byte-stable across runs; the SVGs are equivalent, just not byte-identical.

## Tests

`tests/test_m2_full.py` is a **live crawler integration test**. It needs network access, a real browser session with manual login, and Playwright's Chromium; it writes into `data/` and `logs/`. It cannot pass in a fresh clone and must be excluded from CI. The research pipeline itself has no unit tests — the shipped artifacts in `data/expected_outputs/` and `data/runs/` are the verification baseline instead.

## LLM annotation

Semantic labels were extracted from listing titles with large language models. The three prompt designs are published verbatim under `llm_prompts/` as `prompt_baseline.md`, `prompt_fewshot.md` and `prompt_strict.md` (baseline, few-shot and structured-strict respectively); annotation used the SiliconFlow asynchronous batch API. Sample annotations and raw responses are under `data/samples/`.
